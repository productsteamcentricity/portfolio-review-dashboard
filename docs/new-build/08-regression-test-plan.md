# Regression and acceptance test plan

Phase 0 deliverable 8. Draft of 21 Oct 2026, revised 22 Oct 2026 (Phase 0 review, then D-023 and the MF Screener data
pack) and 22 Oct 2026 (the owner's answers, D-024 to D-033: section 5.6 and the cases they change; change log at the
end of `open-questions.md`). How the new application proves that it preserves the legacy capabilities
(legacy preservation) and meets the brief (the 24 acceptance cases of Phase 15), with the test files, the synthetic
fixtures and the CI gates. Ids: capabilities E-nn and U-nn (`02-capability-inventory.md`), parity rows and BR-n.n
(`05-feature-parity-matrix.md`), milestones M-n (`07-implementation-roadmap.md`).

## 1. Principles

1. **Synthetic or anonymised data only** in automated tests (`CLAUDE.md` rule 6; brief Phase 15). Every fixture is
   generated by code in `tests/fixtures/`; no client file is ever committed. An anonymised real file may be used locally
   only with the owner's approval, outside the repository, and its results are never committed.
2. **Independent known answers** for every financial calculation (`CLAUDE.md` rule 7): the expected value is computed by
   hand or by a separate method, never by the code under test.
3. **Two time zones:** every unit, regression and parity test runs under `TZ=Asia/Kolkata` and `TZ=UTC` (Excel dates
   are time-zone sensitive [TE §9]).
4. **Unrounded comparison** inside the engine (tolerance 1e-9 relative unless stated); display comparisons after the
   renderer's rounding.
5. **Every difference from the legacy is classified** in `tests/parity/ledger.json`; an unclassified difference fails.
6. **Traceability:** each test file starts with a header listing the ids it covers (`// covers: E-25 BR-7.1 AC-01`);
   `scripts/validation/traceability.mjs` (built in M1.3 with the first tests) builds a report that maps every
   parity-matrix row, including the workflow rows W-1 to W-9, to at least one test and fails CI when a row in status
   "in progress" or later has none.

### 5.4 The parity suite
- `tests/parity/*.parity.test.ts` runs the legacy engine (`tools/engine-host.js`, script file, never `node -e`, KI-011)
  and the new engine on the same synthetic books and compares normalised outputs.
- UI-scope legacy calculations (IPS, cost, CVS, MF Analysis, rebalancing state, AI Analyst plan) are compared with
  **golden files** captured once from the legacy page in the browser on the synthetic books
  (`tests/parity/golden/*.json`, procedure in `tests/parity/README.md`), because they cannot run headless [IU U-53].
- Deck and workbook parity compare a normalised inventory (slide titles, component kind, table dimensions, chart types
  and series names; sheet names and header rows), not pixels.
- `ledger.json` entries: `{ id, area, legacyValue, newValue, class: 'improvement' | 'correction' | 'regression',
  reference: 'KI-nnn' | 'OD-nn' | 'BR-n.n', approvedBy?: 'owner' }`. Regressions must be empty for a merge;
  improvements that change client-facing numbers are listed in the PR for the owner.
- **Observations parity** (`parity/observations.parity.test.ts`): for every row of the rule bank's §8 legacy table
  (observation cards L-C1 to L-C8 and SWOT bullets L-S1 to L-T7), a synthetic book built to trigger the legacy
  condition is run through both engines; the mapped rule must fire with the same SWOT quadrant, or the ledger must hold
  the listed classification (threshold change, merged into another rule, or removed such as the unconditional
  rebalancing bullet, N-3). A legacy row with no mapping fails the test.
- **Monthly pipeline parity** (`parity/monthly-pipeline.parity.test.ts`, M11): the legacy `buildtools/` build
  scripts and the new update engine process the same synthetic vendor month; every produced block is compared after
  canonical JSON normalisation. `parity/refdata.parity.test.ts` (M1.3) proves only that `data/refdata/` was
  extracted faithfully from `index.html`; re-derivation from real vendor files is proved by the private local check
  `scripts/monthly-update/parity-local.ts` (September 2026, the month the legacy pipeline reproduced byte for byte),
  whose committed report holds block names, counts, hashes and classifications only.

| Job | Trigger | Steps | Blocking |
|---|---|---|---|
| `checks` (existing) | every PR and push to `main` | legacy invariants, smoke, AI Analyst test, regression | yes |
| `next` (new, M1.1 zero-dependency; extended in M1.2) | every PR and push to `main` | M1.1: `prepush-scan.mjs` over the diff (generic patterns; the deny-list is local only), docs link check, `node --test tests/` in both time zones, AC-21 text cases; M1.3: traceability report; M1.2 onward: `npm ci`; typecheck; unit, regression, parity, exports (with formula evaluation), integration, workflow, acceptance, monthly under `TZ=Asia/Kolkata` and `TZ=UTC`; build twice and compare hashes; `check-next.mjs`; AC-22 | yes |

No ruleset protects `main` (D-033: the owner gave Claude full charge and declined one). `checks` and `next` are
required by practice: a pull request is merged only when both are green (`CLAUDE.md` rule 8), and AC-22 detects a
force-push after the fact.

## 7. Release and pre-push gates (local, before every push, from the first push in M1.1)

1. `scripts/validation/release-check.mjs`: remote URL and default branch as recorded (never changed), current branch,
   `git status` clean except intended files, `git diff --stat` reviewed, no unrelated changes (brief Phase 1, BR-1.1).
2. `scripts/validation/prepush-scan.mjs` with the private deny-list (`PRD_PRIVACY_DENYLIST`): client patterns (PAN,
   e-mail, phone, folio, ARN, client/folio headers), deny-listed names, secrets, local user paths, personal account
   URLs; from M11 also binaries, file classes under `monthly_updates/` and size caps.
3. `npm test`, `npm run build`, `npm run check`, legacy suites (before M1.2: `node --test` and the legacy suites).
4. Office acceptance (`accept-xlsx.ps1`, `accept-pptx.ps1`) when the push changes an exporter or a view-model it
   renders: full recalculation with no error value, Excel equal to the CI evaluator, deck opens without repair.
5. For a monthly cycle: the monthly PRD (hand-written before M14) and the `HANDOVER.md` refresh pass
   `monthly-prd-check.mjs`.
6. `security-release-reviewer` on the staged diff; `financial-domain-reviewer` for financial changes.
7. After push: report the commit SHA, branch, PR link and `git ls-remote` result; never claim a push or deployment
   without that evidence. After a Pages deploy, download the live files and compare hashes (current practice,
   `docs/PROJECT_STATE.md`).

## 9. Limits

- Pixel-level rendering differences between PowerPoint versions, LibreOffice or web viewers are not tested (only
  PowerPoint on the analysts' laptops is in scope).
- Excel itself does not run in CI (no Excel on Linux runners). CI proves formula correctness with the in-house
  evaluator over the writer's allow-listed function subset (section 2); Excel's own recalculation is the local
  differential check, required before any release that changes the workbook. The Excel `XIRR` check column is checked
  only locally.
- The private deny-list is not available in CI; CI runs the generic privacy patterns only, and the local pre-push scan
  is the gate for names.
- Golden files for UI-scope legacy calculations reflect the legacy at `782794f`; if a legacy fix batch changes them, the
  golden file is recaptured and the ledger entry updated in the same PR.
